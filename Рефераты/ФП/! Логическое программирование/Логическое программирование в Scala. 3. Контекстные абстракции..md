### Операции времени компиляции (Compile-time Operations)

Пакет `scala.compiletime` предоставляет методы, которые исполняются исключительно на этапе компиляции[](https://docs.scala-lang.org/scala3/guides/macros/compiletime.html). Они позволяют писать код, который ведёт себя по-разному в зависимости от информации, известной только во время компиляции.

- **`summonFrom`**: Позволяет выполнить условный поиск неявного экземпляра. Это аналог `NotGiven`, но с более гибкой логикой[](https://stackoverflow.com/questions/75779797/type-negation-in-scala-3/75807549#75807549#1).
```scala    
import scala.compiletime.summonFrom
inline def checkForString: String = summonFrom {
  case given String => "String найден!"
  case _ => "String не найден."
}
```
    
- **`summonAll`**: Позволяет найти несколько неявных значений для типов, перечисленных в кортеже[](https://docs.scala-lang.org/scala3/guides/macros/compiletime.html).


### 🧠 Улучшения разрешения `given` (приоритеты)

В Scala 3.7 было изменено правило выбора `given`-экземпляра, чтобы сделать разрешение более предсказуемым[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).

- **Проблема**: В иерархиях классов типов (например, `Functor` <: `Monad` <: `Traverse`) при наличии экземпляров для подтипов компилятор мог не знать, какой именно выбрать[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).
    
- **Решение**: Теперь компилятор выбирает экземпляр с **наиболее общим подтипом (most general subtype)**. Вместо того чтобы выбирать между `Monad[List]` и `Traverse[List]`, он выберет кандидата с самым общим типом — в данном случае `Functor[List]`[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).
    
- **Важно**: Это изменение может нарушить обратную совместимость, если в коде полагались на старую логику выбора, поэтому при миграции на Scala 3.7+ стоит уделить этому внимание[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).

# Сложности и перспективы

#### Недостатки

- **Недетерминизм в доказательствах (Coherence):** Если для одного запроса найдено два разных `given` (два разных доказательства одной теоремы), возникает ошибка компиляции (ambiguity). В классической логике это нормально (у теоремы может быть много доказательств), но для программы важно выбрать ровно одно для предсказуемости. Это ограничивает выразительность: мы не можем просто закодировать все возможные способы решения задачи.

- **Сложность отладки:** «Почему implicit не нашелся?». Вывод типов и поиск given — это черный ящик, гораздо более сложный, чем пошаговая трассировка в Прологе. Пользователь не видит дерево вывода секвенций, которое строил компилятор.
    
- **Время компиляции:** Алгоритм поиска доказательств является NP-полной задачей в общем случае. Сложные программы с развитой иерархией тайп-классов страдают от экспоненциального роста времени компиляции.
    
- **Порог входа:** Требуется глубокое понимание исчисления секвенций, изоморфизма Карри-Ховарда и механик компилятора Scala.
