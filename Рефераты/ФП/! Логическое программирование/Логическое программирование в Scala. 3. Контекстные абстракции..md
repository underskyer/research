Здесь мы рассмотрим основные элементы механизма контекстных абстракций в Scala, разберём один из способов организации автоматической неявной композиции программы, а также обсудим недостатки и перспективы применения контекстных абстракций Scala для техники логического программирования.

# Контекстные абстракции Scala

Суть контекстных абстракций заключена в *механизме вывода термов* — встроенной функции из вселенной типов во вселенную значений (`тип => значение`). В *контексте* вызова такой функции ищется и возвращается значение указанного типа. Алгоритм поиск самостоятельно решает какое именно значение будет возвращено, поэтому значения в контексте называются *неявными*. Таким образом, ключевые аспекты механизма контекстных абстракций — это реализация такой функции, а также способы размещения неявных значений в контекст её вызова.

## Размещение неявных значений

Контексты могут вкладываться один в другой и импортироваться как целиком, так отдельными значениями. Но в любом случае сперва необходимо неявные значения туда *разместить*. Для этого в Scala 3 используется ключевое слово `given` (в более ранних версиях — `implicit`). Вот типичные примеры такого размещения:

```scala
given theAnswer    : Int                                 = 42
given parseArgs    : (args: List[String]) => IO[ScanUrl] = ??? // неявная функция
given headOpt      : [A] => (lst: List[A]) => Option[A]  = ??? // полиморфная неявная функция
given eitherFinctor: [E] => Functor[Either[E, *]]        = ??? // полиморфное значение!
```

Для удобства отладки рекомендуется всегда объявлять имена неявных значения. Но если этого не сделать, то компилятор сгенерирует его сам на основании типа возвращаемого значения и префикса `given_`, например, `given_Functor_Either` или `given_IO_ScanUrl`.

#### !!!! Спойлер !!! Альтернативное размещение значения в контекст
Нестандартный способ размещения значения в контекст — переопределение (overriding) метода базового класса (трейта) так, чтобы к обычным параметрам добавился модификатор `using`. В этом случае пользователи будут как обычно вызывать этот метод через интерфейс базового класса, но в реализации наследника переданный аргумент автоматически попадёт в контекст как неявное значение. Такой приём использовался в первой части обзора при демонстрации [логического стиля](https://habr.com/ru/articles/1064616/#logical) .

Обратите внимание, когда тип `given` записан как функциональный (`parseArgs`, `headOpt`), то так на самом деле описывается неявное значение *результата* этой функции — этот `given` будет задействован при поиске неявного значения по типу этого результата. Все аргументы такой функции будут автоматически вытягиваться из контекста. Замечательно, что тут не имеют значение ни порядок аргументов (нюанс разберём позднее), ни каррированность этой функции: аннотации `given` типами `A => B => C` и `(B, A) => C` аналогичны, так как описывают одно и то же множество аргументов. Если же необходимо разместить в контекст именно значение функционального типа вроде `A => B`, то достаточно в объявлении `given` окружить этот тип скобками, или же определить его псевдоним заранее (так и [было сделано](https://habr.com/ru/articles/1064616/#steps) в первой части обзора).

Многие полезные неявные значения уже добавлены в различные Scala-пакеты, в том числе и во встроенные. Но для некоторых важных экземпляров всё же не существует конкретных `given` ни в каком программном коде. Компилятор сам при необходимости размещает в контекст такие значения. Вот некоторые примеры:
- встроенные предикаты (параметризированные типы-одиночки):
	- двухаргументные отношения типов: `scala.{=:=, <:<}`,
	- одноаргументный `scala.utils.NotGiven[_]`;
- значения для механизма отражений: `scala.reflect.{ClassTag, TypeTag, TypeTest, Manifest}`, `scala.deriving.Mirror`;
- `scala.{CanEqual, ValueOf}`.

Любопытно, что для встроенных приведений типов (подтипизация, или между примитивными типами, вроде `Short => Int`) не предусмотрено неявных значений `Conversion`. Такие преобразования реализованы независимо от того, что называется контекстными абстракциями в Scala и пересекаются с ними зачастую неочевидным образом.

## Извлечение неявных значений

В языке предусмотрено несколько различных способов извлечения значений из контекста:
- магия призыва:
	- `summon[T]`
	- `summonAll[(T1, T2, …)]` 
	- `summonInline[T]` 
	- `summonFrom[T](f: Nothing => T)`
- контекстный аргумент функции:
	- модификатор аргумента `using`.
	- тип контекстной функции (например, `A ?=> B`) — по сути, псевдоним для класса контекстной функции с методом вида `def apply(using a: A): B`.
- контекстные границы (`A: F`), ограничивающие типы определёнными классами — синтаксический сахар над требованием неявного предоставления экземпляров классов типов.



Среди различных неявных значений выделяются *неявные преобразования типов* `Conversion[A, B]`, представляющие собой обычные функции вида `A => B`. Помимо стандартного способа извлечения из  контекста, такие преобразования могут *неявно встраиваться* в вашу программу компилятором. Это происходит автоматически, когда он встречает использование терма одного типа там, где ожидается другой:
```scala
class A()  
class B()  
  
given ba: Conversion[B, A] = b =>  
  println("ba conversion")  
  A()  
  
val a: A = B() // компилятор автомачески заменит на ba(B())
```


### !!! контекстные границы и классы типов

Кстати, приведение от подтипа к супертипу (связанных наследованием) разработчики языка сочли настолько тривиальным, что никаких встроенных неявных `Conversion` для них не предусмотрено. Если же вручную разместить такой `given`, то извлечь его из контекста получится, но это преобразование никогда не будет задействовано неявно.

- Локальный контекст
	- **Локальные объявления:** неявные значения (`implicit val`/`implicit def` в Scala 2 или `given` в Scala 3), объявленные прямо в текущем блоке кода, методе или классе.
	- **Родительские области:** значения, объявленные во внешних (охватывающих) классах или трейтах текущей области видимости.
	- **Импорты:** значения, явно или полностью (через `_` или `*`) импортированные в текущий файл/область из других пакетов или объектов.
- Контекст типа
	- Объект компаньон типа
	- Контекст типов-параметров
	- Outer objects for nested types
	- Other dimensions

### Операции времени компиляции (Compile-time Operations)

Пакет `scala.compiletime` предоставляет методы, которые исполняются исключительно на этапе компиляции[](https://docs.scala-lang.org/scala3/guides/macros/compiletime.html). Они позволяют писать код, который ведёт себя по-разному в зависимости от информации, известной только во время компиляции.

- **`summonFrom`**: Позволяет выполнить условный поиск неявного экземпляра. Это аналог `NotGiven`, но с более гибкой логикой[](https://stackoverflow.com/questions/75779797/type-negation-in-scala-3/75807549#75807549#1).
```scala    
import scala.compiletime.summonFrom
inline def checkForString: String = summonFrom {
  case given String => "String найден!"
  case _ => "String не найден."
}
```
    
- **`summonAll`**: Позволяет найти несколько неявных значений для типов, перечисленных в кортеже[](https://docs.scala-lang.org/scala3/guides/macros/compiletime.html).


### 🧠 Улучшения разрешения `given` (приоритеты)

В Scala 3.7 было изменено правило выбора `given`-экземпляра, чтобы сделать разрешение более предсказуемым[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).

- **Проблема**: В иерархиях классов типов (например, `Functor` <: `Monad` <: `Traverse`) при наличии экземпляров для подтипов компилятор мог не знать, какой именно выбрать[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).
    
- **Решение**: Теперь компилятор выбирает экземпляр с **наиболее общим подтипом (most general subtype)**. Вместо того чтобы выбирать между `Monad[List]` и `Traverse[List]`, он выберет кандидата с самым общим типом — в данном случае `Functor[List]`[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).
    
- **Важно**: Это изменение может нарушить обратную совместимость, если в коде полагались на старую логику выбора, поэтому при миграции на Scala 3.7+ стоит уделить этому внимание[](https://www.scala-lang.org/2024/08/19/given-priority-change-3.7.html).

# Недостатки и перспективы

#### Недостатки

- **Недетерминизм в доказательствах (Coherence):** Если для одного запроса найдено два разных `given` (два разных доказательства одной теоремы), возникает ошибка компиляции (ambiguity). В классической логике это нормально (у теоремы может быть много доказательств), но для программы важно выбрать ровно одно для предсказуемости. Это ограничивает выразительность: мы не можем просто закодировать все возможные способы решения задачи.

- **Сложность отладки:** «Почему implicit не нашелся?». Вывод типов и поиск given — это черный ящик, гораздо более сложный, чем пошаговая трассировка в Прологе. Пользователь не видит дерево вывода секвенций, которое строил компилятор.
    
- **Время компиляции:** Алгоритм поиска доказательств является NP-полной задачей в общем случае. Сложные программы с развитой иерархией тайп-классов страдают от экспоненциального роста времени компиляции.
    
- **Порог входа:** Требуется глубокое понимание исчисления секвенций, изоморфизма Карри-Ховарда и механик компилятора Scala.
