## Рекурсор


В MLTT принято определять типы посредством правил четырёх видов:
- formation (образование, формулирование) фиксирует отличительную сигнатуру семейства типов, структуру его записи;
- introduction (введение) задаёт конструкторы типа;
- elimination (устранение) задаёт способы использования его значений;
- computation (вычисление) показывает, как именно «уничтожаются» все конструкторы типа.

Вот как можно реализовать тип натуральных чисел в Scala:
```scala
enum Nat:                          // formation
  case Zero            extends Nat // introduction (1-й конструктор)
  case Succ(prev: Nat) extends Nat // introduction (2-й конструктор)
```
В первой строке мы объявляем новый тип `Nat` — это правило *формулирования*, затем два конструктора типа со своими сигнатурами (правила введения). Перечисление в Scala уже предполагает использование его значений через сопоставление с шаблонами, но давайте выпишем такую функцию явно:
```scala
val rec: [C] => (C, Nat => C => C) => Nat => C =          // elimination
  [C] => (z, next) =>
    case Nat.Zero       => z                              // computation 1
    case Nat.Succ(prev) => next(prev)(rec(z, next)(prev)) // computation 2
```
Функция `rec` «*устраняет*» значения типа `Nat` (последний аргумент функции), *вычисляя* значения любых типов из каждого конструктора. Таким образом получается последние два правила определения типа.

Правила вычисления очень важны при определении типа. Например, мы могли бы второю ветку в `rec` сделать идентичной первой и везде возвращать `z`. Это фактически уравняло бы разные конструкторы типа, превратив любые функции на нём в константные. Семантика типа оказалась бы несколько поломанной: разные конструкторы порождают неэквивалентные значения, но *любое* их использование приводит к эквивалентным результатам. Тем не менее, с точки зрения категории типов выбранного языка программирования набору конструкторов соответствует функтор, которому сопоставляется начальная алгебра или конечная коалгебра ([предел или копредел](https://habr.com/ru/articles/970762/)) — вполне можно считать, что их универсальное свойство фиксирует правила вычислений и, следовательно, сам тип с точностью до изоморфизма.

Натуральные числа буквально воплощают идею индукции — последовательного вычисления новых данных на основе начальных условий. Обратите внимание на элиминатор: он принимает на вход начальное условие `z: C`, шаг индукции `next: Nat => C => C` и разворачивает результат типа `C`, *рекурсивно* сворачивая натуральное число. Поэтому такую функцию обычно называют `rec` — *рекурсор*. Посмотрим, как его можно использовать, например, для вычисления факториала:
```scala
type FactState = (index: Int, result: Long)  
  
val factorial = rec[FactState](  
  (index = 0, result = 1L),  
  _ => (currentLong, currentFact) =>  
    val nextLong = currentLong + 1  
    (nextLong, currentFact * nextLong)  
).andThen(_.result)  
  
import Nat.*  
val five: Nat = Succ(Succ(Succ(Succ(Succ(Zero)))))  
  
factorial(five) // 120L
```
Обратите внимание, мы игнорируем сам индекс типа `Nat`, так как не можем использовать его напрямую в арифметических выражениях. Но именно `Nat` обеспечивает остановку рекурсии.

## !!! БРЕД !!! Свёртка неподвижной точки
Представленный выше рекурсор является *свёрткой* рекурсивного типа `Nat`. Подобные типы мы уже рассматривали в [другом обзоре](https://habr.com/ru/articles/863324/) — их можно выразить через *неподвижную точку* соответствующих конструкторов типов. В нашем случае это может выглядеть так:
```scala
enum NatFunctor[A]: // параметризтиованное перечисление - конструктор типов
  case Zero             extends NatFunctor[Nothing]
  case Succ[P](prev: P) extends NatFunctor[P]

case class Fix[F[_]](unfix: F[Fix[F]]) // неподвижная точка конструктора типов
  
type Nat = Fix[NatFunctor] // натуральные числа!
  
import NatFunctor.*

// конструкторы (asInstanceOf нужен как костыль для хилого механизма вывода типов)
val zero = Fix[NatFunctor](Zero.asInstanceOf[NatFunctor[Nat]])  
def succ[P <: Nat](prev: P) = Fix[NatFunctor](Succ(prev).asInstanceOf[NatFunctor[Nat]])  

// рекурсор
val rec: [C] => (C, Nat => C => C) => Nat => C =  
  [C] => (default, next) =>  
    case Fix(Zero)       => default  
    case Fix(Succ(prev)) => next(prev)(rec(default, next)(prev))
```

Основное преимущество использования неподвижной точки заключается в том, что в её *универсальную функцию свёртки* можно вынести всю рекурсию из рекурсора. Но его сигнатура по прежнему связана со структурой типа. Причём связь взаимно однозначная — сигнатура рекурсора кодирует тип независимо от того, как именно он реализован.

## ???    Кодирование Чёрча     ????

Показанные выше реализации типа натуральных чисел по своей природе *индуктивны* — их конструкторы позволяют по индукции разворачивать всё более и более сложные структуры данных, тогда как за их свёртку отвечает рекурсор. Но возможен и дуальный подход, когда весть тип строится на основе сигнатуры рекурсивной свёртки. Поэтому такой способ описания типа называется *рекурсивным*.

Посмотрим как это устроено. Сперва выберем другую неподвижную точку в виде полиморфной функции:
```scala
infix type ~>[F[_], G[_]] = [A] => F[A] => G[A] // недоестественное преобразование
type Algebra[F[_]] = [A] =>> F[A] => A          // алгебра функтора — «распаковка»
type Id[A] = A                                  // тождественный функтор
type μ[F[_]] = Algebra[F] ~> Id                 // функциональная неподвижная точка функтора

def cata[F[_]]: Algebra[F] ~> (μ[F] => *) =     // катаморфизм - свёртка неподвижной точки функтора
  [A] => alg => _(alg)
// требуется опция компилятора `-Xkind-projector`
```
Здесь в угоду сложившейся терминологии конструкторы типов называются функторами, хотя сама функториальность, честная реализация `map`, явно не требуется.

В определении функтора для натуральных чисел мы избавимся от наследования — спрячем его в `Either`:
```scala
infix type +[A, B] = A Either B

object Zero  
type Zero = Zero.type // Zero ≅ Unit ≅ 𝟙
case class Succ[Prev](prev: Prev)  
  
type NatFunctor[A] = Zero + Succ[A] // функтор - не самостоятельный тип, а псевдоним выражения
```

И теперь мы можем описать натуральные числа в виде полиморфной функции:
```scala  
type Nat = μ[NatFunctor] // [A] => (Zero Either Succ[A] => A) => A

// конструкторы ленивых функций
val zero: Nat            = [A] => alg => alg(Left(Zero))  
def succ(prev: Nat): Nat = [A] => alg => alg(Right(Succ(prev(alg))))  
  
// рекурсия спрятана в катаморфизм
val rec: [C] => (C, Nat => C => C) => Nat => C =  
  [C] => (z, next) => n =>  
    cata[NatFunctor][C](_.fold[C](
      _ => z,
      s => next(n)(s.prev)
	))(n)
```

Подобное выражение типа в виде функции называется *кодировкой Чёрча*, лежащей в основе [исчисления конструкций](https://ru.wikipedia.org/wiki/%D0%98%D1%81%D1%87%D0%B8%D1%81%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5_%D0%BA%D0%BE%D0%BD%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%86%D0%B8%D0%B9) (CoC). С кодированием Чёрча контекст не засоряется новыми типами, так как мы имеем дело с функциями, оперирующими лишь известными базовыми типами (в примере используются типы `Zero`, `Succ` и `Either`, но от них тоже можно избавиться). Это минимизирует ядро языка и библиотек, но имеет ряд концептуальных недостатков:
- так как все данные не хранятся в памяти, а являются ленивыми функциями, во многих сценариях заметно снижается скорость вычислений;
- жадная β-редукция скрывает реализацию функций, лишая возможности их сравнивать — это усложняет работу и программисту, и компилятору;
- часто кодировка Чёрча допускает существование экзотических значений, которых невозможно получить конструкторами исходного типа;
- обилие функций значительно усложняет отладку.

Удачным решением оказалось дополнить чистый CoC возможностью использования индуктивных определений типов. Поэтому в таких языках как Rocq и Lean сейчас реализуется *исчисление индуктивных конструкций* (CIC).


## Семейство зависимых типов

Все наши рекурсоры принимают по два параметра, а в теле по очереди производится сопоставление с двумя шаблонами. Это обусловлено тем, что итоговый тип натуральных чисел опирается ровно на два типа-конструктора: `Zero` и `Succ`, и порядок их обработки фиксирован. Значит каждый из этих типов имеет свой *индекс*, известный на этапе компиляции. Этот индекс может быть одним из двух вариантов, что соответствует *значениям* булевского типа $\mathbb{2}$. В результате мы имеем *семейство типов, зависящих от значения*:
$$
\begin{split}
&NatFammily: \mathbb{2} \to \mathcal{U} \to \mathcal{U}
\\
&\begin{split}
&NatFammily(false)(\_) &&\equiv Zero
\\
&NatFammily(true) &&\equiv Succ
\end{split}
\end{split}
$$
Здесь под $\mathcal{U}$ понимается совокупность типов рассматриваемой вселенной (**u**niversum).

В Scala такое семейство удобно реализовать с помощью сопоставления с литеральными типами:
```scala
type 𝔹 = Boolean & Singleton

type NatFamily[Prev] = [B <: 𝔹] =>> B match
  case false => Zero       // литеральный тип false
  case true  => Succ[Prev] // литеральный тип true
```
Литеральные типы переносят зависимость от значений на уровень типов, сводя определение новых типов к привычному параметрическому полиморфизму.

Вот пара примеров использования полученного семейства типов:
```scala
val zero: NatFamily[Nothing][false] = Zero  
val one:  NatFamily[Zero   ][true ] = Succ(Zero)
```
В этом примере в обоих случаях индекс был задан вручную. Однако тип натуральных чисел (как и многие другие индуктивные типы) зависит не от конкретных индексов, но от их типа. Чтобы использовать `NatFamily` как самодостаточную конструкцию необходима *квантификация* — связывание свободного параметра `B` в выражении `NatFamily[B <: 𝔹]` кванторами. 

## Зависимые функции и пары 

В математике базовыми являются кванторы всеобщности $\forall$ и существования $\exists$. В MLTT квантификация может осуществляться по значениям, типам, видам типов и т.д. — в любых вселенных типов. Стандартные кванторы здесь обобщаются до *конструкторов типов* $\Pi$ и $\Sigma$. Теперь мы имеем дело не просто с абстрактными суждениями, но с конкретным описанием структуры значений — *конструктивных доказательств* обитаемости этих типов. Давайте посмотрим, как они устроены.

Запишем правила их определения в стандартной для теории типов и логики *нотации естественного вывода* (мы уже встречались с ней в [обзоре по логическому программированию](https://habr.com/ru/articles/1067788/#semantics)):
$$
\begin{gather}
\quad
&
\Pi
&\qquad&
\Sigma

\\
\\

Form\colon\quad
&
\frac{\Gamma \vdash A\colon \mathcal{U}\quad \Gamma ,x\colon A\vdash B(x)\colon \mathcal{U}}{\Gamma \vdash \prod\limits_{x\colon A} B(x)\colon \mathcal{U}}
&\qquad&
\frac{\Gamma \vdash A\colon \mathcal{U}\quad \Gamma ,x\colon A\vdash B(x)\colon \mathcal{U}}{\Gamma \vdash \sum\limits_{x\colon A}B(x)\colon \mathcal{U}}

\\
\\

In\colon\quad
&
\frac{\Gamma ,x\colon A\vdash b\colon B(x)}{\Gamma \vdash (\lambda x.b)\colon \prod\limits_{x\colon A} B(x)}
&\qquad&
\frac{\Gamma \vdash a\colon A\quad \Gamma \vdash b\colon B(a)}{\Gamma \vdash (a,b)\colon \sum\limits_{x\colon A}B(x)}

\\
\\

Elim\colon\quad
&
\frac{\Gamma \vdash f\colon \prod\limits_{x\colon A} B(x)\quad \Gamma \vdash a\colon A}{\Gamma \vdash f(a)\colon B(a)}
&\qquad&
\frac{\Gamma \vdash p\colon \sum\limits_{x\colon A}B(x)}{\Gamma \vdash \pi _{1}(p)\colon A}
\qquad
\frac{\Gamma \vdash p\colon \sum\limits_{x\colon A}B(x)}{\Gamma \vdash \pi _{2}(p)\colon B(\pi _{1}(p))}

\\
\\

Comp\colon\quad
&
(\lambda x.b)(a)\equiv b[a/x]
&\qquad&
\pi _{1}(a,b)\equiv a \quad \pi _{2}(a,b)\equiv b
\end{gather}
$$
Отсюда видно, что $\Pi$-тип описывает *произведение* типов семейства по всем значениям базового типа. При использовании значений такого произведения необходимо передавать $a\colon A$, чтобы *получить* нужную проекцию. Это даёт *зависимую функцию* $(a: A) \to B(a)$, у которой не только сам результат, но и его *тип* определяются значением переданного аргумента.

В свою очередь, $\Sigma$-тип представляет собой *сумму* всех типов семейства. Чтобы *создать* экземпляр этой суммы нужно помимо него передать и значение $a\colon A$, выступающее в роли «индекса конструктора». Так что в результате получаются *зависимые пары* $\big(a\colon A,\, b\colon B(a)\big)$ с двумя проекциями, возвращающими индекс и целевое значение.

> [!NOTE] Категорная картина: ослабление и его сопряжённые
>Самое чистое объяснение — через проекцию контекста:
$p\colonΓ,a\colon A \to Γ$
Она забывает aa. У неё есть обратный образ (ослабление):
$$
p^∗\colon \mathcal{U}(Γ)→\mathcal{U}(Γ,a\colon A)
$$
который любой тип из Γ «поднимает» в расширенный контекст, игнорируя aa. Кванторы — это **сопряжённые** к $p^∗$:
$$
Σ_a⊣p^∗⊣Π_a​
$$
Подстановка $t∗$ для сечения $t\colonΓ→Γ,a\colon A$ — это ещё один функтор в том же направлении, но не сопряжённый, а обратный к $p∗$ на сечении.
Π и Σ — это функторы, которые спускают объект из расслоения в базу. Зачем спускать? Потому что вся работа — композиция, универсальные свойства, пределы, гомотопии — происходит в базе. Расслоение нужно, чтобы _описывать_ зависимость; база — чтобы _работать_.

Каноническая реализация функции, тип результата которой зависит от значения уже встроена в язык, но также может быть полезна функция, зависящая не от значения а только от типа:
```scala
type ℿ[Index, F[_ <: Index]] = (i: Index) => F[i.type]
```

Если нужен тип $\prod_{A\colon \mathcal{U}}B(A)$, индекс которого пробегает не по значениям, а по всем типам сразу, то его можно закодировать как обычную полиморфную функцию `type Π[B[_]] = [A] => () => B[A]`. Иза ограничений языка здесь не обойтись без нелепых скобочек `()`, поэтому вместо этого типа мы будем использовать такую стрелку:
```scala
infix type ~>[F[_], G[_]] = [A] => F[A] => G[A] // ≅ Π[[A] =>> F[A] => G[A]]
```

Тип зависимой пары мы реализуем так:
```scala
enum ⅀[Index, +F[_ <: Index]]:  
  case InΣ[Ind, G[_ <: Ind], J <: Ind](index: J, value: G[index.type]) extends ⅀[Ind, G]  

export ⅀.InΣ
```
Конструктор `InΣ` прячет экзистенциальный индекс `index: J` вместе с его типом за фасадом `⅀`. Эти данные можно вытащить при сопоставлении значений `⅀` с шаблоном `InΣ`.

## Алгебра типов

В MLTT обычные алгебраические операции над типами *определяются* через конструкторы зависимых пар и функций:
$$
\begin{split}
&Pair: \mathbb{2} \to \mathcal{U}
\qquad\text{семейство типов}
\\
&Pair(0) = A
\\
&Pair(1) = B
\\\\
A + B &\equiv \sum_{b: \mathbb{2}} Pair(b)
\\
A \times B &\equiv \sum_{x: A} B \cong \prod_{b: \mathbb{2}} Pair(b)
\\
A \to B &\equiv \prod_{x: A} B
\end{split}
$$

Несложно заметить, как обобщить формулу для произведения типов на кортежи произвольной длины — достаточно описать нужное индексированное семейство типов и построить $\Pi$-тип по его размеру.

```scala
// изоморфизм типов
infix type ≅[A, B] = (  
  forward : A => B,  
  backward: B => A  
)
infix type ×[A, B] = (A, B)  
infix type +[A, B] = A Either B

// семейство типов, зависящих от Bool
type Pair[A, B] = [R <: 𝔹] =>> R match  
  case false => A  
  case true  => B

type Sum[A, B] = ⅀[𝔹, Pair[A, B]]  
  
def sumIso[A, B]: (A + B) ~ Sum[A, B] = (  
  forward = _.fold[Sum[A, B]](  
    InΣ[𝔹, Pair[A, B], false](false, _),  
    InΣ[𝔹, Pair[A, B], true](true, _)  
  ),  
  backward =  
    case InΣ(false, a: A) => Left(a)  
    case InΣ(true,  b: B) => Right(b)  
)

// произведение через ∑
type ProdΣ[A, B] = ⅀[A, Const[B]]  
def prodΣIso[A, B]: (A × B) ≅ ProdΣ[A, B] = (  
  forward = ΣIn[A, Const[B], A].tupled,  
  backward = { case ΣIn(a: A, b: B) => a -> b }  
)

// произведение через Π
type ProdΠ[A, B] = ℿ[Bool, Pair[A, B]]  
def prodΠIso[A, B]: (A × B) ≅ ProdΠ[A, B] = (  
  forward = ab =>  
    case _: false => ab._1  
    case _: true  => ab._2,  
  backward = p => p(false) -> p(true)  
)

// экспоненциал
type Exp[A, B] = ℿ[A, Const[B]]  
def expIso[A, B]: (A => B) ≅ Exp[A, B] = (  
  forward = identity,  
  backward = f => f(_)  
)
```

## Тип рекурсора

Каждый индуктивный тип $T$ является *начальной алгеброй* соответствующего эндофунктора $In_T\colon \mathcal{U} \to \mathcal{U}$ в категории типов $\mathcal{U}$. Эндофунктор описывает сумму сигнатур отдельных конструкторов значений типа $T$. Тип, как начальная алгебра, выражается через *наименьшую неподвижную точку* $\mu$ (см. [отдельный обзор](https://habr.com/ru/articles/863324/)):
$$
T = \mu\, In_T \equiv \mu X\colon \mathcal{U}.\, In_T(X)
$$
так, что существует естественный изоморфизм $In_T(T) \cong T$, дающий единый конструктор $in\colon In_T(T) \to T$. Универсальное свойство задаётся функцией *свёртки* (fold), которая в MLTT называется *рекурсорм*:

$$
rec_T: \prod_{R\colon\mathcal{U}} (In_T(R) \to R) \to (T \to R).
$$
Это полиморфная функция, универсально определённая для любого типа результата $R$: «если скажешь, как извлечь из контейнера $In_T$ значение $R$, то получишь возможность свернуть значение типа $T = \mu\, In_T$ в $R$».

>Напомню, действие кванторов $\sum$ и $\prod$ распространяется до конца выражения или непарной закрывающей скобки, *независимо от наличия стрелок*.

Учитывая, как кодируется $\Pi$-тип, мы можем записать тип рекурсора неподвижной точки `T = Fix[In]` функтора `In[+_]` так:
```scala
type Algebra[F[_]] = [A] =>> F[A] => A // извлечение значения
infix type ~>[F[_], G[_]] = [A] => F[A] => G[A]

type Recursor[In[+_]] = Algebra[In] ~> (Fix[In] => *)
```

Стоит заметить, что в теории категорий стрелку `~>` обычно ассоциируют с [естественным преобразованием](https://habr.com/ru/articles/951574/) функторов, но в данном случае это не так. Дело в том, что конструктор типов `Algebra[In][_]` на самом деле *инвариантен*, поэтому такое преобразование в принципе не обладает свойством естественности. Тем не менее, инвариантные конструкторы типов сопоставляются с диагональными компонентами соответствующих *профункторов*, и тогда стрелка `~>` выступает в роли их *диестественного преобразования* (в [обзоре по категориям типов](https://habr.com/ru/articles/1023452/#dinat) для них использовалось обозначение `⇻`).


## Индуктор

Построенные выше рекурсоры отлично справлялись с «устранением» значений типа натуральных чисел — позволяли вычислять на их основе значения произвольного типа. Но теперь-то мы умеем работать не только с простыми, но и с *зависимыми типами*, и для работы с ними обычного рекурсора уже не достаточно.

Эту задачу решает более общий элимиантор — *индуктор*. Он таже предназначен для разврётки значений индуктивного типа $T=\mu\,In_T$, но в отличие от рекурсора, вычисляет значения не единственного типа $R\colon \mathcal{U}$, но целого индексированного семейства $R(t\colon T)\colon \mathcal{U}$, называемого *мотивом индукции*. Точнее, принимая на вход *зависимую алгебру* функтора $In_T$ для мотива $R(t)$ индуктор возвращает *зависимую функцию* $\prod_{t\colon T}R(t)$.

Зависимую алгебру часто расписывают во Чёрчу как функцию высшего порядка, так что для натуральных чисел тип индуктора получается таким:
$$
ind_{\mathbb{N}} : \prod_{R\colon\mathbb{N} \to U}
R(zero) \to \left(\prod_{n:\mathbb{N}} R(n) → R(succ(n))\right) \to
\prod_{n:\mathbb{N}}R(n).
$$
Рекурсор является частным случаем индуктора с константным мотивом $Const_R(n) \equiv R$:
$$
rec_{\mathbb{N}}: \prod_{R\colon\mathcal{U}} R \to (\mathbb{N} \to R \to R) \to (\mathbb{N} \to R) = ind_{\mathbb{N}}\,Const_R
$$

Чтобы как можно точнее реализовать тело этого индуктора, нам придётся переписать сам тип натуральных чисел. Прежде всего, выберем такую индуктивную версию конструктора неподвижной точки:
```scala
enum μᵢ[+F[+_]]:  
  case In[+G[+_], +V <: G[μᵢ[G]]](unfix: V) extends μᵢ[G]
```
Модификаторы типов-параметров, отдельный тип `V` для хранимого значения и сокрытие деталей с помощью наследования — все эти мелкие подсказки помогают компилятору Scala работать с зависимыми типами. Теперь тип натуральных чисел мы можем определить через эту неподвижную точку от функтора, представляющую сумму способов создания числа:
```scala
object Zero  
type Zero = Zero.type  
final case class Succ[+P](prev: P)  
  
type NatFunctor[+Prev] = Zero + Succ[Prev]  // Either
  
type Nat =               μᵢ[NatFunctor]  
type NatZero =           μᵢ.In[NatFunctor, Left [Zero,    Nothing]]  
type NatSucc[N <: Nat] = μᵢ.In[NatFunctor, Right[Nothing, Succ[N]]]
```
Мы получили тип `Nat` и совокупность его подтипов вроде `NatSucc[NatSucc[NatZero]] <:< Nat`. Конструкторы значений запишем так:
```scala
val zero:                 NatZero    = μᵢ.In[NatFunctor, Left [Zero,    Nothing]](Left(Zero))  
def succ[N <: Nat](n: N): NatSucc[N] = μᵢ.In[NatFunctor, Right[Nothing, Succ[N]]](Right(Succ(n)))

val n1 = succ(zero)  
val n2 = succ(n1)
val n3 = succ(n2)
```

Теперь запишем наш зависимый индуктор:
```scala
type NatInductor = [R[_ <: Nat]]  
  => R[NatZero] => ((p: Nat) => R[p.type] => R[NatSucc[p.type]]) // зависимая алгебра  
  => ℿ[Nat, R]  
  
val ind: NatInductor =  
  [R[_ <: Nat]] => default => next => n => n match  
    case μᵢ.In(Left(_)) => default.asInstanceOf[R[n.type]]  
    case μᵢ.In(Right(value)) =>  
      val p = value.asInstanceOf[Succ[Nat]].prev  
      next(p)(ind(default)(next)(p)).asInstanceOf[R[n.type]]
      
def rec[C] = ind[Const[C]] // рекурсор
```
Здесь опять видны костыли, помогающие механизму вывода типов. В первую очередь, это множественные `asInstanceOf`, подсказывающие компилятору, казалось бы, очевидные факты. Ещё одним компромиссом стал отказ от честного типа `C[Succ[p.type]]` в зависимой алгебре в пользу более общего `C[Nat]` — без такой правки при тестировании сломается сопоставление с шаблоном `NatSucc` в мотиве индукции.

Для проверки решим следующую задачу: по заданному числу вернуть кортеж такой размерности, заполненный одинаковыми значениями `42: Int`. Разные числа дают значения *разных типов кортежа*.

Определим функцию `cloneTheAnswer` через индуктор, использующий мотив `TupleFamily`:
```scala
type TupleFamily[N <: Nat] <: Tuple = N match  
  case μᵢ.In[NatFunctor, Left [Zero,    Nothing]] => EmptyTuple            // NatZero
  case μᵢ.In[NatFunctor, Right[Nothing, Succ[p]]] => Int *: TupleFamily[p] // NatSucc[p]
  
val cloneTheAnswer: ℿ[Nat, TupleFamily] =  
  ind[TupleFamily](EmptyTuple)(_ => prevP => 42 *: prevP)
```
Нынешняя версия компилятора плохо понимает сочетание типов-псевдонимов и сопоставления с шаблонами типов. Поэтому приходится либо явно раскрывать все псевдонимы в мотиве (мы так и сделали), либо раскидывать ещё больше `asInstanceOf`. Как бы то ни было, метод оказывается вполне рабочим:
```scala
val r0: EmptyTuple      = cloneTheAnswer(zero) // ()
val r1: Tuple1[Int]     = cloneTheAnswer(n1)   // (42)
val r2: (Int, Int)      = cloneTheAnswer(n2)   // (42, 42)
val r3: (Int, Int, Int) = cloneTheAnswer(n3)   // (42, 42, 42)
```


## Фундированные типы

В [обзоре о рекурсивных типах](https://habr.com/ru/articles/863324/#type_fixed_point) говорилось, что неподвижные точки есть не у всех конструкторов типов. Необходимым условием является *ковариантность*, иначе тип неподвижной точки не удастся даже нормализовать. Но даже если этот тип нормализуется, это не является гарантией того, что существуют конструктивные алгоритмы создания его значений.

«Хорошими» являются неподвижные точки только тех конструкторов типов, чей тип-параметр находится строго в *положительных позициях* — «правее всех стрелок». Их также называют *полиномиальными*, так как часто их можно представить в виде суммы степеней параметра с какими-то коэффициентами и выразить в виде *зависимой пары*:
$$
\begin{split}
&
\mathbb{P}\colon (I \to \mathcal{U}) \to (\mathcal{U} \to \mathcal{U}),
\\
&
\mathbb{P}(B)(X)
= i + i' \times X^{B(i')} + i'' \times X^{B(i'')} + \ldots
= \sum_{i\colon I} X^{B(i)}
= \sum_{i\colon I} \prod_{b\colon B(i)} X.
\end{split}
$$
Значениями полиномиального функтора будут зависимые пары $(i\colon I, B(i) \to X)\colon \mathbb{P}(B)(X)$.

Важный момент: значений у типов $I$ и $B(i)$ может быть не только бесконечно много, но они могут даже образовывать *несчётное множество* (например, $I=\mathbb{N}^\mathbb{N}$). Для таких типов просто не существует алгоритма последовательного перебора значений, но тем не менее, индексированные ими $\Sigma$- и $\Pi$-типы всё так же полезны на практике.

Наименьшие неподвижные точки полиномиальных конструкторов типов описывают различного вида деревья. Несмотря на возможную бесконечность ветвей в узлах, все эти деревья будут *конечной* высоты. 

>Фундированность гарантирует ровно одну вещь: **любой путь от корня до листа конечен**. В дереве нет бесконечных «вертикальных» путей вниз.

Неподвижная точки полиномиального функтора, построенного для семейства типов $B(i)$ называются *фундированным* (**W**ell Founded, хорошо обоснованными) типом и обозначается $\mathbb{W}_{i\colon I}B(i)$:
$$
\begin{split}
&
\mathbb{W}_{i\colon I}B(i) \cong 
 μ\mathbb{P}(B)=
 μX.\sum_{i\colon I}Subtrees​(i),
\\
&
Subtrees(i) = \prod_{b\colon B(i)} W \equiv B(i) \to W.
\end{split}
$$
Зависимая функция $Subtrees(i)$ перечисляет поддеревья во всех $B(i)$ ветвях узла разновидности $i\colon I$.

Мы записали лишь изоморфизм $W$-типа, а определяется он аналогично $\Sigma$- и $\Pi$-типам через правила формирования, введения, удаления и вычисления. Дело в том, что в отличие от квантора $\mu$, допускающего неконструктивные типы, $W$-тип является *фундаментальным примитивом* MLTT.

Конструктор $sup\colon Sup$ для типа $𝑊 ≡𝕎_{𝑖:𝐼}𝐵(𝑖)$ отражает саму концепцию неподвижной точки полиномиального функтора, как его *начальной алгебры* (напомню, алгебру функтора можно воспринимать, как способ его распаковки: $\mathrm{Alg}_F(X) = F(X) \to X$):
$$
Sup = Alg_{\mathbb{P}}(W) =
\prod _{i:I} Subtrees(i) \to W =
\left(\sum_{i:I} Subtrees(i)\right) \to W .
$$
На вход он принимает правило, по которому для каждой разновидности узла $i:I$ можно построить его поддеревья. Название конструктора заимствовано из [теории ординалов](https://ru.wikipedia.org/wiki/%D0%9F%D0%BE%D1%80%D1%8F%D0%B4%D0%BA%D0%BE%D0%B2%D0%BE%D0%B5_%D1%87%D0%B8%D1%81%D0%BB%D0%BE): фундированное дерево — это *наименьшая верхняя граница* (supremum) его поддеревьев. Из последнего равенства видно, что значения W-типа представляют собой зависимые пары $(i\colon I, st\colon Subtrees(i))$.

Рекурсор $W$-типа — это обычная свёртка неподвижной точки полиномиального функтора:
$$
rec_{\mathbb{W}}: \prod_{R\colon \mathcal{U}} Alg_{\mathbb{P}}(R) \to (W \to R).
$$
Чтобы получить индуктор, нужно обобщить рекурсор на случай зависимого мотива $R\colon W \to \mathcal{U}$. Например, функция справа от стрелки ставится зависимой:
$$
ind_{\mathbb{W}}: \prod_{R:W\to\mathcal U} \widehat{Alg}(R)
\to
\prod_{w:W}R(w).
$$
Здесь семейство типов алгебр $\widehat{Alg}(R)$ обобщает понятие алгебры полиномиального функтора $\mathrm{Alg}_{\mathbb{P}}(R) = \big(\sum_{i\colon I} \prod_{b\colon B(i)} R\big) \to R$. Нужно учесть, что мотив $R$ теперь зависит от значения типа $W$, которое представляет собой пару $(i, st)\colon W$, так что получается такое выражение:
$$
\widehat{Alg}(R) = \prod_{(i, st)\colon W}
\left(\prod_{b\colon B(i)}R(st(b))\right) \to
R(i, st).
$$
Алгебра описывает один шаг индукции — распаковку узла $(i, st)\colon W$ в $R(i, st)$ при заданных правилах распаковки его ветвей. Эти правила называются *гипотезой индукции* $ih(i, st)\colon \prod_{b\colon B(i)}R(st(b))$. Обратите внимание — тип гипотезы зависит от *результата вычисления функции* $st(b)$ для каждой ветки $b$ и некого набора поддеревьев $st$. Позднее мы обсудим, как это влияет на механизм проверки типов.

Правило вычисления элиминатора $ind_{\mathbb W}$ на конструкторе $sup$ выглядит так:
$$
ind_{\mathbb W}(R)(alg)(sup(i, st)) =
alg(i, st)\big(\lambda b\colon B(i).\ ind_{\mathbb W}(R)(alg)(st(b))\big).
$$

Натуральные числа строятся через W-тип следующим образом:
$$
\begin{split}
&NatArity(b\colon \mathbb{2}) = \\
& \qquad b = 0 \mapsto \mathbb{0}\\
& \qquad b = 1 \mapsto \mathbb{1},
\\\\
&\mathbb{N} = \mathbb{W}_{b\colon \mathbb{2}} NatArity(b).
\end{split}
$$


Например, вот строится тип обычного бинарного дерева $T$ со значениями $A$ в узлах:
$$
\begin{split}
&
I\colon \mathcal{U} = \mathbb{1} + A
\\
&
\text{конструторы:}\quad
inl\colon \mathbb{1} \to I,
\quad
inr\colon A \to I;
\\ \\
&
B\colon I \to \mathcal{U},
\\
&
B(inl(\star\colon \mathbb{1})) = \mathbb{0} \quad \text{(лист)},
\qquad
B(inr(a)) = \mathbb{2} \quad \text{(две ветви)};
\\\\
&
\mathbb{P}(B)(X)
= \sum_{i: 1 + A}X^{B(i)}
\cong X^{B(inl(\star))} + \sum_{a: A}X^{B(inr(a))}
\cong 1 + A \times X^\mathbb{2};
\\
&
T = \mathbb{W}_{a\colon \mathbb{1} + A}B(a) \cong
\mu X.\, \mathbb{P}(B)(X) \cong 1 + A \times T \times T.
\end{split}
$$

### !!! СПОЙЛЕР !!!! Коиндуктивный M-тип

В MLTT существует и конструкция, дуальная фундированным типам — коиндуктивные *нефундированные* (non-well-founded) M-типы. Буква «M» — это как бы «перевёрнутая W», но чаще её обосновывают понятием ***M**aximal fixed point*. Тогда как W-типы являются начальными алгебрами полиномиального функтора, M-типы представляют собой финальные коалгебры:
$$
\mathbb{M}_{i\colon I}B(i) \cong \nu \mathbb{P}(B) =
\nu X.\sum_{i\colon I}B(i) \to X.
$$

$$
corec_{M}:\prod _{S\colon \mathcal{U}}(S\rightarrow In_{M}(S))\rightarrow (S\rightarrow M)
$$

## Заключение

Фиксированные универсальным свойством функции делятся на входящие (конструкторы) и исходящие (проекторы). Тип можно рассматривать как промежуточную точку между типами-аргументами конструкторов и результирующими типами проекторов. Следовательно, тип описывается совокупностью *комбинаций* каждого проектора со всеми конструкторами. Каждая такая комбинация «уничтожает» упоминание нашего типа.

Парадоксальный момент — тип описывается не просто типом функции Чёрча, но конкретной реализацией (значением!) функции уничтожения.








Первый вариант `Σᴄʜɪʀᴄʜ` представляет собой характерную для исчисления конструкций кодировка Чёрча экзистенциального типа. В значениях этого типа скрыты тип `I <: Index` и значение типа `F[I]`, поэтому для использования необходимо представить функцию распаковки, полиморфную по всем индексам `I`. Кодировка Чёрча очень элегантна, но в Scala приводит к колоссальным издержкам и при написании кода (часто приходится вручную ломать типизацию), и на этапе компиляции (сильно усложняя вывод типов), и во время исполнения (аллокации полиморфных функций для рекурсивных типов), и в отладке (жуткие стеки вызовов из-за CPS).

*Зависимый от пути* тип `Σᴏᴏᴘ` хранит в своих экземплярах помимо `F[I]` как тип индекса так и его значение. Это сильно упрощает вывод типов и реализацию логики использования проекций зависимой пары. Ценой же является ослабление типобезопасности за счёт стирания ([erasure](https://ru.wikipedia.org/wiki/%D0%A1%D1%82%D0%B8%D1%80%D0%B0%D0%BD%D0%B8%D0%B5_%D1%82%D0%B8%D0%BF%D0%B0)) и расширения (widening) типов.
