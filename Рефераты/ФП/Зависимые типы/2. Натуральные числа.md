## Рекурсор


В MLTT принято определять типы посредством правил четырёх видов:
- formation (образование, формулирование) фиксирует отличительную сигнатуру семейства типов, структуру его записи;
- introduction (введение) задаёт конструкторы типа;
- elimination (уничтожение) задаёт способы использования его значений;
- computation (вычисление) показывает, как именно «уничтожаются» все конструкторы типа.

Вот как можно реализовать тип натуральных чисел в Scala:
```scala
enum Nat:                          // formation
  case Zero            extends Nat // introduction (1-й конструктор)
  case Succ(prev: Nat) extends Nat // introduction (2-й конструктор)
```
В первой строке мы объявляем новый тип `Nat` — это правило *формулирования*, затем два конструктора типа со своими сигнатурами (правила введения). Перечисление в Scala уже предполагает использование его значений через сопоставление с шаблонами, но давайте выпишем такую функцию явно:
```scala
val rec: [C] => (C, Nat => C => C) => Nat => C =          // elimination
  [C] => (z, next) =>
    case Nat.Zero       => z                              // computation 1
    case Nat.Succ(prev) => next(prev)(rec(z, next)(prev)) // computation 2
```
Функция `rec` «*уничтожает*» значения типа `Nat` (последний аргумент функции), *вычисляя* значения любых типов из каждого конструктора. Таким образом получается последние два правила определения типа.

Правила вычисления очень важны при определении типа. Например, мы могли бы второю ветку в `rec` сделать идентичной первой и везде возвращать `z`. Это фактически уравняло бы разные конструкторы типа, превратив любые функции на нём в константные. Семантика типа оказалась бы несколько поломанной: разные конструкторы порождают неэквивалентные значения, но *любое* их использование приводит к эквивалентным результатам. Тем не менее, с точки зрения категории типов выбранного языка программирования набору конструкторов соответствует функтор, которому сопоставляется начальная алгебра или конечная коалгебра ([предел или копредел](https://habr.com/ru/articles/970762/)) — вполне можно считать, что их универсальное свойство фиксирует правила вычислений и, следовательно, сам тип с точностью до изоморфизма.

Натуральные числа буквально воплощают идею индукции — последовательного вычисления новых данных на основе начальных условий. Обратите внимание на элиминатор: он принимает на вход начальное условие `z: C`, шаг индукции `next: Nat => C => C` и *рекурсивно* сворачивает натуральное число, получая результат типа `C`. Поэтому такую функцию обычно называют `rec` — *рекурсор*. Посмотрим, как его можно использовать, например, для вычисления факториала:
```scala
type FactState = (index: Int, result: Long)  
  
val factorial = rec[FactState](  
  (index = 0, result = 1L),  
  _ => (currentLong, currentFact) =>  
    val nextLong = currentLong + 1  
    (nextLong, currentFact * nextLong)  
).andThen(_.result)  
  
import Nat.*  
val five: Nat = Succ(Succ(Succ(Succ(Succ(Zero)))))  
  
factorial(five) // 120L
```
Обратите внимание, мы игнорируем сам индекс типа `Nat`, так как не можем использовать его напрямую в арифметических выражениях. Но именно `Nat` обеспечивает остановку рекурсии.

## Свёртка неподвижной точки
Представленный выше рекурсор является *свёрткой* рекурсивного типа `Nat`. Подобные типы мы уже рассматривали в [другом обзоре](https://habr.com/ru/articles/863324/) — их можно выразить через *неподвижную точку* соответствующих конструкторов типов. В нашем случае это может выглядеть так:
```scala
enum NatFunctor[A]: // параметризтиованное перечисление - конструктор типов
  case Zero             extends NatFunctor[Nothing]
  case Succ[P](prev: P) extends NatFunctor[P]

case class Fix[F[_]](unfix: F[Fix[F]]) // неподвижная точка конструктора типов
  
type Nat = Fix[NatFunctor] // натуральные числа!
  
import NatFunctor.*

// конструкторы (asInstanceOf нужен как костыль для хилого механизма вывода типов)
val zero = Fix[NatFunctor](Zero.asInstanceOf[NatFunctor[Nat]])  
def succ[P <: Nat](prev: P) = Fix[NatFunctor](Succ(prev).asInstanceOf[NatFunctor[Nat]])  

// рекурсор
val rec: [C] => (C, Nat => C => C) => Nat => C =  
  [C] => (default, next) =>  
    case Fix(Zero)       => default  
    case Fix(Succ(prev)) => next(prev)(rec(default, next)(prev))
```

Основное преимущество использования неподвижной точки заключается в том, что в её *универсальную функцию свёртки* можно вынести всю рекурсию из рекурсора. Но его сигнатура по прежнему связана со структурой типа. Причём связь взаимно однозначная — сигнатура рекурсора кодирует тип независимо от того, как именно он реализован.

## Кодирование Чёрча

Показанные выше реализации типа натуральных чисел по своей природе *индуктивны* — их конструкторы позволяют по индукции разворачивать всё более и более сложные структуры данных, тогда как за их свёртку отвечает рекурсор. Но возможен и дуальный подход, когда весть тип строится на основе сигнатуры рекурсивной свёртки. Поэтому такой способ описания типа называется *рекурсивным*.

Посмотрим как это устроено. Сперва выберем другую неподвижную точку в виде полиморфной функции:
```scala
infix type ~>[F[_], G[_]] = [A] => F[A] => G[A] // недоестественное преобразование
type Algebra[F[_]] = [A] =>> F[A] => A          // алгебра функтора — «распаковка»
type Id[A] = A                                  // тождественный функтор
type μ[F[_]] = Algebra[F] ~> Id                 // функциональная неподвижная точка функтора

def cata[F[_]]: Algebra[F] ~> (μ[F] => *) =     // катаморфизм - свёртка неподвижной точки функтора
  [A] => alg => _(alg)
// требуется опция компилятора `-Xkind-projector`
```
Здесь в угоду сложившейся терминологии конструкторы типов называются функторами, хотя сама функториальность, честная реализация `map`, явно не требуется.

В определении функтора для натуральных чисел мы избавимся от наследования — спрячем его в `Either`:
```scala
infix type +[A, B] = A Either B

object Zero  
type Zero = Zero.type // Zero ≅ Unit ≅ 𝟙
case class Succ[Prev](prev: Prev)  
  
type NatFunctor[A] = Zero + Succ[A] // функтор - не самостоятельный тип, а псевдоним выражения
```

И теперь мы можем описать натуральные числа в виде полиморфной функции:
```scala  
type Nat = μ[NatFunctor] // [A] => (Zero Either Succ[A] => A) => A

// конструкторы ленивых функций
val zero: Nat            = [A] => alg => alg(Left(Zero))  
def succ(prev: Nat): Nat = [A] => alg => alg(Right(Succ(prev(alg))))  
  
// рекурсия спрятана в катаморфизм
val rec: [C] => (C, Nat => C => C) => Nat => C =  
  [C] => (z, next) => n =>  
    cata[NatFunctor][C](_.fold[C](
      _ => z,
      s => next(n)(s.prev)
	))(n)
```

Подобное выражение типа в виде функции называется *кодировкой Чёрча*, лежащей в основе [исчисления конструкций](https://ru.wikipedia.org/wiki/%D0%98%D1%81%D1%87%D0%B8%D1%81%D0%BB%D0%B5%D0%BD%D0%B8%D0%B5_%D0%BA%D0%BE%D0%BD%D1%81%D1%82%D1%80%D1%83%D0%BA%D1%86%D0%B8%D0%B9) (CoC). С кодированием Чёрча контекст не засоряется новыми типами, так как мы имеем дело с функциями, оперирующими лишь известными базовыми типами (в примере используются типы `Zero`, `Succ` и `Either`, но от них тоже можно избавиться). Это минимизирует ядро языка и библиотек, но имеет ряд концептуальных недостатков:
- так как все данные не хранятся в памяти, а являются ленивыми функциями, во многих сценариях заметно снижается скорость вычислений;
- жадная β-редукция скрывает реализацию функций, лишая возможности их сравнивать — это усложняет работу и программисту, и компилятору;
- часто кодировка Чёрча допускает существование экзотических значений, которых невозможно получить конструкторами исходного типа;
- обилие функций значительно усложняет отладку.

Удачным решением оказалось дополнить чистый CoC возможностью использования индуктивных определений типов. Поэтому в таких языках как Rocq и Lean сейчас реализуется *исчисление индуктивных конструкций* (CIC).


## Семейство зависимых типов

Все наши рекурсоры принимают по два параметра, а в теле по очереди производится сопоставление с двумя шаблонами. Это обусловлено тем, что итоговый тип натуральных чисел опирается ровно на два типа-конструктора: `Zero` и `Succ`, и порядок их обработки фиксирован. Значит каждый из этих типов имеет свой *индекс*, известный на этапе компиляции. Этот индекс может быть одним из двух вариантов, что соответствует *значениям* булевского типа $\mathbb{2}$. В результате мы имеем *семейство типов, зависящих от значения*:
$$
\begin{split}
&NatFammily: \mathbb{2} \to \mathcal{U} \to \mathcal{U}
\\
&\begin{split}
&NatFammily(false)(\_) &&\equiv Zero
\\
&NatFammily(true) &&\equiv Succ
\end{split}
\end{split}
$$
Здесь под $\mathcal{U}$ понимается совокупность типов рассматриваемой вселенной (**u**niversum).

В Scala такое семейство удобно реализовать с помощью сопоставления с литеральными типами:
```scala
type NatFamily[Prev] = [B] =>> B match
  case false => Zero       // литеральный тип false
  case true  => Succ[Prev] // литеральный тип true
```
Литеральные типы переносят зависимость от значений на уровень типов, сводя определение новых типов к привычному параметрическому полиморфизму.

Вот пара примеров использования полученного семейства типов:
```scala
val zero: NatFamily[Nothing][false] = Zero  
val one:  NatFamily[Zero][true ]    = Succ(Zero)
```
В этом примере в обоих случаях индекс был задан вручную. Однако тип натуральных чисел (как и многие другие индуктивные типы) зависит не от конкретных индексов, но от их типа. Чтобы использовать `NatFamily` как самодостаточную конструкцию необходима *квантификация* — связывание свободного параметра `B` в выражении `NatFamily[B <: Bool]` кванторами. 

## Зависимые функции и пары 

В математике базовыми являются кванторы всеобщности $\forall$ и существования $\exists$. В MLTT квантификация может осуществляться по значениям, типам, видам типов и т.д. — в любых вселенных типов. Стандартные кванторы здесь обобщаются до *конструкторов типов* $\Pi$ и $\Sigma$. Теперь мы имеем дело не просто с абстрактными суждениями, но с конкретным описанием структуры значений — *конструктивных доказательств* обитаемости этих типов. Давайте посмотрим, как они устроены.

Запишем правила их определения в стандартной для теории типов и логики *нотации естественного вывода* (мы уже встречались с ней в [обзоре по логическому программированию](https://habr.com/ru/articles/1067788/#semantics)):
$$
\begin{gather}
\quad
&
\Pi
&\qquad&
\Sigma

\\
\\

Form\colon\quad
&
\frac{\Gamma \vdash A\colon \mathcal{U}\quad \Gamma ,x\colon A\vdash B(x)\colon \mathcal{U}}{\Gamma \vdash \prod\limits_{x\colon A} B(x)\colon \mathcal{U}}
&\qquad&
\frac{\Gamma \vdash A\colon \mathcal{U}\quad \Gamma ,x\colon A\vdash B(x)\colon \mathcal{U}}{\Gamma \vdash \sum\limits_{x\colon A}B(x)\colon \mathcal{U}}

\\
\\

In\colon\quad
&
\frac{\Gamma ,x\colon A\vdash b\colon B(x)}{\Gamma \vdash (\lambda x.b)\colon \prod\limits_{x\colon A} B(x)}
&\qquad&
\frac{\Gamma \vdash a\colon A\quad \Gamma \vdash b\colon B(a)}{\Gamma \vdash (a,b)\colon \sum\limits_{x\colon A}B(x)}

\\
\\

Elim\colon\quad
&
\frac{\Gamma \vdash f\colon \prod\limits_{x\colon A} B(x)\quad \Gamma \vdash a\colon A}{\Gamma \vdash f(a)\colon B(a)}
&\qquad&
\frac{\Gamma \vdash p\colon \sum\limits_{x\colon A}B(x)}{\Gamma \vdash \pi _{1}(p)\colon A}
\qquad
\frac{\Gamma \vdash p\colon \sum\limits_{x\colon A}B(x)}{\Gamma \vdash \pi _{2}(p)\colon B(\pi _{1}(p))}

\\
\\

Comp\colon\quad
&
(\lambda x.b)(a)\equiv b[a/x]
&\qquad&
\pi _{1}(a,b)\equiv a \quad \pi _{2}(a,b)\equiv b
\end{gather}
$$
Отсюда видно, что $\Pi$-тип описывает *произведение* типов семейства по всем значениям базового типа. При использовании значений такого произведения необходимо передавать $a\colon A$, чтобы *получить* нужную проекцию. Это даёт *зависимую функцию* $(a: A) \to B(a)$, у которой не только сам результат, но и его тип определяются значением переданного аргумента.

В свою очередь, $\Sigma$-тип представляет собой *сумму* всех типов семейства. Чтобы *создать* экземпляр этой суммы нужно помимо него передать и значение $a\colon A$, выступающее в роли «индекса конструктора». Так что в результате получаются *зависимые пары* $\big(a\colon A,\, b\colon B(a)\big)$ с двумя проекциями, возвращающими индекс и целевое значение.

> [!NOTE] Категорная картина: ослабление и его сопряжённые
>Самое чистое объяснение — через проекцию контекста:
$p\colonΓ,a\colon A \to Γ$
Она забывает aa. У неё есть обратный образ (ослабление):
$$
p^∗\colon \mathcal{U}(Γ)→\mathcal{U}(Γ,a\colon A)
$$
который любой тип из Γ «поднимает» в расширенный контекст, игнорируя aa. Кванторы — это **сопряжённые** к $p^∗$:
$$
Σ_a⊣p^∗⊣Π_a​
$$
Подстановка $t∗$ для сечения $t\colonΓ→Γ,a\colon A$ — это ещё один функтор в том же направлении, но не сопряжённый, а обратный к $p∗$ на сечении.
Π и Σ — это функторы, которые спускают объект из расслоения в базу. Зачем спускать? Потому что вся работа — композиция, универсальные свойства, пределы, гомотопии — происходит в базе. Расслоение нужно, чтобы _описывать_ зависимость; база — чтобы _работать_.

В MLTT обычные  алгебраические операции над типами *определяются* через конструкторы зависимых пар и функций:
$$
\begin{split}
AB&: \mathbb{2} \to \mathcal{U}
\qquad\text{семейство типов}
\\
&AB(0) = A
\\
&AB(1) = B
\\\\
A + B &\equiv \sum_{b: \mathbb{2}} AB(b)
\\
A \times B &\equiv \sum_{x: A} B \cong \prod_{b: \mathbb{2}} AB(b)
\\
A \to B &\equiv \prod_{x: A} B
\end{split}
$$
Помимо алгебраических операций теперь доступны и более интересные типы. Например, не сложно заметить, как обобщить формулу для произведения типов на кортежи произвольной длины — достаточно описать нужное индексированное семейство типов и построить $\Pi$-тип по его размеру. А вот так с помощью квантора неподвижной точки $\mu$ можно представить тип натуральных чисел:
$$
\mathbb{N} = \mu\,X.\, \sum_{b:2} NatFamily[b][X].
$$

В Scala зависимую пару можно закодировать разными способами:
```scala
type Σᴄʜɪʀᴄʜ[IndexType, F[_ <: IndexType]] = [Y] => ([I <: IndexType] => F[I] => Y) => Y

trait Σᴏᴏᴘ  [IndexType, F[_ <: IndexType]]:  
  type I <: IndexType // первая проекция  
  val fi: F[I]        // вторая проекция  
  
enum Σɪɴᴅ[IndexType, G[_ <: IndexType]]: //  
  case In[I, F[_ <: I], i <: I](fi: F[i], index: i) extends Σɪɴᴅ[I, F]
  
type ∑ = Σᴏᴏᴘ
```

Первый вариант представляет собой ООП-шный класс с двумя проекторами — «скрытый» тип-свидетель и, собственно, само значение. Второй вариант — это характерная для исчисления конструкций кодировка Чёрча экзистенциального типа. Наконец третье индуктивное определение будет наиболее удобным для большинства сценариев, так как «скрытый» тип остаётся доступным во время компиляции при сопоставлении шаблонов.

```scala
type ∏[Index, F[_ <: Index]] = (i: Index) => F[i.type] // честная зависимая функция
type Π[Index, F[_ <: Index]] = [I <: Index] =>> F[I]   // чисто на уровне типов
```

### Почему Структурный Сигма-тип — лучший выбор?

1. Идеальная синергия с Match Types («Прозрачность» для компилятора)

Тайпчекер Scala 3 спроектирован вокруг концепции **Path-Dependent Types** (типов, зависящих от путей). Когда индекс зафиксирован как открытый тип-член (`type Tag`), для компилятора он является «прозрачным».

- В структурном варианте при вызове `myInductor` компилятор точно знает, что `n1.term.unfix.Tag` — это литерал `false`. Ему не нужно гадать, и он может мгновенно свести (reduce) `TupleFamily` на этапе компиляции.
- В **GADT-Enum** и **Черч-кодировании** информация о типе скрыта за параметрами методов или конструкторов. Scala 3 часто пасует перед необходимостью раскрыть Match Type, когда селектор является абстрактным параметром типа (отсюда и возникали ошибки `failed since selector ... does not match`).

2. Минимизация `asInstanceOf` в пользовательском коде

Поскольку структурная Сигма не скрывает свои типы, вы можете писать высокоуровневые комбинаторы, не прибегая к грубым приведениям типов. Вы получаете строгую гарантию: если у вас есть объект, у него есть поле `.tag`, и его тип строго равен подтипу `IndexType`. В GADT-Enum нам пришлось дважды матчить рантайм-значение, а в Черч-кодировании — полностью стереть типы до `Any` внутри индуктора.

3. Предсказуемость в рантайме (Отсутствие лишних аллокаций)

- В кодировке **Черча** на каждый шаг рекурсии индуктора создается новая полиморфная функция (замыкание). Для больших чисел Пеано это создаст огромную нагрузку на Garbage Collector (GC) из-за генерации тысяч промежуточных объектов-лямбд.
    
- Структурный трейт компилируется в обычный Java-интерфейс с геттерами. Это стандартный, хорошо оптимизированный паттерн для JVM.

---

Почему остальные два варианта хуже для этой задачи?

- **GADT-Enum (`SigmaEnum`)** — великолепно подходит для _обычного_ прикладного кода (где типы не зависят от рантайм-значений динамически). Но в Scala 3 реализация GADT страдает «размытием» литералов (Widening): тип `true` внутри Enum часто превращается в `Boolean`, из-за чего ломается строгая индукция. Этот вариант слишком хрупок для элиминаторов.
- **Кодировка Черча (`Σᴄʜɪʀᴄʜ`)** — прекрасна с академической точки зрения (так как позволяет выразить Сигму в системе типов без поддержки пар), но превращает код в CPS-ад (Continuation-Passing Style). Нам пришлось полностью отключить тайпчекер с помощью кастов к `Any`, чтобы компилятор просто пропустил индуктор. Это сводит на нет саму идею безопасной зависимой типизации.

> Уравнитель можно рассматривать как способ выделить из множества (или типа) тех элементов, для которых два способа обработки дают одинаковый результат. Это полезно, когда нужно отфильтровать или проверить согласованность данных. 
> В языках с зависимыми типами (например, Agda, Coq) уравнители используются для моделирования равенств и доказательств того, что два выражения равны.

## Заключение

Фиксированные универсальным свойством функции делятся на входящие (конструкторы) и исходящие (проекторы). Тип можно рассматривать как промежуточную точку между типами-аргументами конструкторов и результирующими типами проекторов. Следовательно, тип описывается совокупностью *комбинаций* каждого проектора со всеми конструкторами. Каждая такая комбинация «уничтожает» упоминание нашего типа.

Парадоксальный момент — тип описывается не просто типом функции Чёрча, но конкретной реализацией (значением!) функции уничтожения.
