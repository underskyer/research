
# 1. Что компилятор действительно делает особенно с `=:=` — implicit search

Здесь есть **хардкод в компиляторе** (в `scala.tools.nsc.typechecker.Implicits` / `SyntheticMethods`). Ключевые механизмы:

**а) Синтез `refl` для definitional equality.** Когда implicit search ищет `A =:= B`, компилятор **не ищет инстанс в scope** — он проверяет, дефиниционально ли равны `A` и `B` (с учётом редукции type aliases, refinement'ов, singleton types). Если да — возвращает канонический `singleton_=:=`. Это специальный случай в `Implicits.scala` (`typedImplicit` для `=:=`/`<:<`).

```scala

implicitly[Int =:= Int]              // ✔ компилятор синтезирует refl
implicitly[List[Int] =:= List[Int]]  // ✔
// implicitly[Int =:= String]        // ❌ implicit not found
```
**б) `<:<` синтезируется через subtyping.** Для `A <:< B` компилятор проверяет `A <: B` (conformance), а не ищет инстанс. `=:=` — частный случай: `A =:= B` синтезируется, если и `A <: B`, и `B <: A`.

**в) Приоритет над пользовательскими инстансами.** Даже если в scope есть `implicit val weird: Int =:= String = ...asInstanceOf...`, компилятор для `Int =:= Int` предпочтёт синтезированный `refl`. Специальная логика в `Implicits` гарантирует, что «настоящий» `refl` выигрывает.

# 2. GADT-вывод при pattern matching — вот где компилятор «особенно обрабатывает» равенства

Хотя матчить по `=:=` нельзя, компилятор **сам порождает** `=:=`-свидетельства при матчинге GADT-подобных типов. Это вторая важная специальная обработка.

**Scala 3** (полноценный GADT-вывод):

```scala
sealed trait Expr[T]
case class IntLit(n: Int) extends Expr[Int]
case class BoolLit(b: Boolean) extends Expr[Boolean]
def eval[T](e: Expr[T]): T = e match {
  case IntLit(n)  => n   // компилятор выводит T =:= Int в этой ветке
  case BoolLit(b) => b   // и T =:= Boolean здесь
}
```

Внутри ветки компилятор **неявно добавляет** свидетельство `T =:= Int` в контекст вывода типов (это `GADT`-уточнение в `Typer`/`Infer`). Вы его не видите, но именно оно позволяет `n : Int` вернуть как `T`. Это ближайший аналог J-правила в Scala — но работает только для **GADT-паттернов** (case-классы с индексами), а не для произвольного `=:=`.

**Scala 2** — то же самое, но менее надёжно; сложные GADT требуют явного протаскивания `=:=`:

```scala
def eval[T](e: Expr[T]): T = e match {
  case IntLit(n) => n.asInstanceOf[T]  // часто приходилось так
}
```

# 3. Другие специальные механизмы компилятора вокруг `=:=`/`<:<`

**а) `@implicitNotFound`** — стандартное сообщение об ошибке для `=:=`. Это не «специальная обработка типа», но компилятор знает про аннотацию.

**б) Автоматическое `<:<`/`=:=` в implicit-параметрах методов коллекций.** В Scala 2 стандартная библиотека (`scala.Predef.$conforms`, `=:=`, `<:<`) интегрирована: например, `List[A] <:< List[B]` синтезируется через вариантность. Специальной магии в компиляторе для этого нет — работает обычный implicit search + subtyping.

**в) `evidence$N`-параметры.** Когда вы пишете `def f[A](a: A)(implicit ev: A =:= Int)`, компилятор генерирует скрытый параметр `evidence$1: A =:= Int` и передаёт его в байткод. Это обычная кодогенерация implicit-параметров, но `=:=`/`<:<` участвуют в ней постоянно.

**г) Erasure: `=:=` стирается в `Object`.** `ev(a)` в байткоде — это `ev.apply(a)` через `Function1`, но после erasure — просто `a` (identity). Компилятор знает, что `=:=`/`<:<` — «фантомные» свидетельства, и оптимизирует их вызовы. Это в `Erasure.scala` (`isSynthetic`/special-casing для `Function1`-наследников).

**д) Scala 3: `scala.=:=` / `scala.<:<` объявлены с `@implicitNotFound` и специальной обработкой в `Implicits.scala`** — синтез `refl` идёт через `synthesized`-путь, минуя обычный поиск в scope. Это ключевое отличие от пользовательских типов: **для `=:=` implicit search имеет встроенное правило рефлексивности**, а для `MyEvidence[A,B]` — нет.

**е) `Match types` и `=:=` (Scala 3).** Компилятор может использовать `=:=` в выводе match types, но это не «специальная обработка `=:=`», а общий механизм редукции.

# 4. Чего компилятор НЕ делает (важно для вашего вопроса)

- **Не даёт pattern match по `=:=`** с уточнением типов (нет J через матчинг).
    
- **Не выводит нетривиальные равенства** (`Either[A,B] =:= Either[B,A]` не синтезируется).
    
- **Не делает `substituteCo` автоматическим** — его нужно вызывать явно.
    
- **Не рефлектирует `=:=` в definitional equality** (экстенсиональность не добавлена): из `ev: A =:= B` нельзя получить, что `A` и `B` дефиниционально равны в других контекстах — только явно применить `ev`/`substituteCo`.
    

# 5. Сводка: где компилятор «особенно обрабатывает» `=:=`

|Механизм|Что делает|Где в компиляторе|
|---|---|---|
|Синтез `refl`|`A =:= B` синтезируется, если `A ≡ B` definitionally|`Implicits` (спец. правило)|
|`<:<` через subtyping|`A <:< B` — если `A <: B`|`Implicits` + `Typechecker`|
|GADT-уточнение при матчинге|Неявно добавляет `T =:= Int` в ветку `case IntLit`|`Typer`/`Infer` (GADT)|
|Erasure|`=:=`/`<:<` стираются, вызовы оптимизируются|`Erasure`|
|`@implicitNotFound`|Стандартное сообщение|`Implicits`|
|Приоритет `refl`|Синтезированный `refl` выигрывает у пользовательских инстансов|`Implicits`|

**Чего нет:** pattern matching по `=:=` как по индуктивному типу (J через матчинг), вывода нетривиальных равенств, автоматического `substitute`. Именно поэтому `=:=` в Scala — «бедный родственник» identity type из MLTT: компилятор даёт вам **синтез `refl`** и **GADT-уточнение**, но не даёт **элиминатор J через матчинг** и **нетривиальные доказательства**.

Так что на ваш вопрос: «поддерживается ли при сопоставлении с шаблонами» — **нет, не по самому `=:=`**; но **GADT-матчинг** — это механизм, где компилятор _порождает_ `=:=`-уточнения неявно, и это ближайший аналог. Специальная обработка `=:=` в компиляторе — это прежде всего **implicit search с правилом рефлексивности**, а не pattern matching.
